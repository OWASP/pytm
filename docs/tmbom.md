# pytm → CycloneDX 2.0 TM-BOM mapping

Generated by `python tm.py --tmbom` (`pytm/tmbom.py`). Schema: CycloneDX 2.0
draft, pinned to `CycloneDX/specification@906c57979d786c935787213ae1693a98097858ce`
(`schema/2.0`). The schema is unpublished and may change.

Conventions:

* `pytm:x` means a TM-BOM `properties` entry named `pytm:x` (value always a
  string). Used when the schema has no field for the pytm attribute.
* `bom-ref` values are `<kind>-<slug(name)>`, with `-2`, `-3`... on collision.
  They are stable across runs for an unchanged model.
* Empty/unset values are omitted rather than emitted as `""`/`[]`.

## New pytm attributes and elements

Added so that the export no longer has to leave TM-BOM fields empty. All are
optional and default to "unknown", in which case the field is omitted.

| pytm `element.attribute` | Type / values | TM-BOM field | Notes |
|--------------------------|---------------|--------------|-------|
| `Threat.stride`, `Finding.stride` | `unassigned` (default), `spoofing`, `tampering`, `repudiation`, `information-disclosure`, `denial-of-service`, `elevation-of-privilege` (`"Information Disclosure"` is normalised; empty means `unassigned`) | `threats.threats[].categories[]` as `{taxonomy: "STRIDE", category}` | The bundled threat library assigns none, so every library threat is `unassigned`. The TM-BOM schema only allows the six STRIDE values in `category`, so `unassigned` cannot be written to the BOM: `categories` is simply omitted for those threats. Set `stride` on custom threats, or on a `Finding` override, to export it. |
| `Threat.impact`, `Finding.impact` | `negligible`, `low`, `moderate`, `major`, `catastrophic` | `risks.risks[].inherentRisk.impact.level` | Empty in the threat library: impact depends on the system. Set it on a `Threat`, or per element via an override `Finding(threat_id=..., impact="major")`. |
| `Threat.capec`, `Finding.capec` | `list[int]`; parsed from `references` (URLs or `CAPEC-n`) unless given | `threats.attackPatterns[]` (`capecId`, `name: "CAPEC-n"`), referenced from `threats.threats[].attackPatterns` | One attack pattern per distinct id; the pattern has no description because pytm only knows the id. |
| `Threat.cwe`, `Finding.cwe` | `list[int]`; parsed from `references` unless given | `threats.threats[].weaknesses[]` as `{cweId}` | |
| `Actor.kind` | `ActorKind`: `UNKNOWN` (default), `PERSON`, `ORGANIZATION`, `SYSTEM`, `PERSONA` | `blueprints[].actors[]` with `party` | `PERSON`/`ORGANIZATION` -> `party.person.name` / `party.organization.name`; `SYSTEM` -> `party.system.kind = software-system`; `PERSONA` -> `party.persona` (archetype `administrator` if `isAdmin`, else `end-user`). Party `roles` is mandatory in the schema, so a role is chosen from `isAdmin` (`operator` / `end-user`). System and persona parties, and `actors[]` itself, have no name field, so the name goes into `description` and `pytm:name`. `UNKNOWN` keeps the old behaviour (an asset of type `actor`). Flows reference the actor's `bom-ref` either way. |
| `Dataflow.isEncrypted` | `Optional[bool]`, default `None` (unknown) | `flows[].encrypted` | Takes precedence over the `tlsVersion` inference, so a flow can be explicitly `False`. |
| `Control` (new element) | see below | `controls[]` | New class; registered with the `TM` like `Data`; part of `--json` output/input as top-level `controls`. Not to be confused with `Controls`, the per-element boolean flags. |
| `Control.name`, `.description` | `str` | `controls[].name`, `.description` | |
| `Control.category` | `ControlCategory`: `UNKNOWN`, `PREVENTIVE`, `DETECTIVE`, `CORRECTIVE`, `COMPENSATING`, `DETERRENT`, `RECOVERY` | `controls[].category` | |
| `Control.status` | `ControlStatus`: `UNKNOWN`, `RECOMMENDED`, `PROPOSED`, `APPROVED`, `REJECTED`, `PLANNED`, `IN_PROGRESS`, `IMPLEMENTED`, `VERIFIED`, `DECOMMISSIONED` | `controls[].status` | Default is `UNKNOWN` (omitted) so declaring a control never silently claims it is implemented. |
| `Control.mitigates` | `list[str]` of threat SIDs (a `Threat` or one SID is accepted) | `threats.threats[].mitigations` (refs to the control) and `risks[].responses[].controls` | A risk links a control only when the SID matches and `appliesTo` is empty or contains the finding's element. A linked control with no explicit `Finding.response` gives the risk a `reduce` response. Linking does **not** change findings or `resolve()`: a threat is still reported as a finding even if a control mitigates it. |
| `Control.appliesTo` | `list[Element]` (any element, flow or boundary); empty = whole model | `controls[].appliesTo` | Elements that never appear in the BOM are dropped from the list. |
| `Control.effectiveness` | `ineffective`, `marginal`, `adequate`, `good`, `excellent` | `controls[].effectiveness.rating` | Validated on assignment. |

### Existing attributes that are now mapped

| pytm `element.attribute` | TM-BOM field | Notes |
|--------------------------|--------------|-------|
| `Data.isDestEncryptedAtRest` / `Data.isSourceEncryptedAtRest` | `dataSets[].placements[].encrypted` | A placement is created for each data store the data flows into (only if `Data.isStored`) or out of. `encrypted` is emitted only when true. **`check()` overwrites both flags from the stores' `controls.isEncryptedAtRest`**, so set that on the `Datastore`, not on the `Data`. |
| `Dataflow.usesSessionTokens` | `flows[].authentication` = custom `{name: "session-token"}` | The schema's `sessionManagement` (on boundaries) has no "uses tokens" flag, only token lifetimes and logout behaviour; a custom authentication type was the closest honest fit. |
| `Data.credentialsLife` | property `pytm:credentialsLife` | No schema field. Note `check()` sets it to `UNKNOWN` for credential data without a lifetime. |
| `Dataflow.response` | `flows[].synchronous = true` on the request flow | A flow that has a response is request/response. `bidirectional` is not used because the response is already emitted as its own flow. |

## 1. Document level

| pytm | TM-BOM | Notes / caveats |
|------|--------|-----------------|
| (generated) | `$schema`, `specFormat: "CycloneDX"`, `specVersion: "2.0"`, `version: 1` | `$schema` points at the pinned raw GitHub schema URL. |
| (generated) | `serialNumber` | New `urn:uuid:` each run, so two runs of an identical model differ. `version` is always 1; pytm does not track BOM revisions. |
| (generated) | `metadata.timestamp` | UTC, seconds resolution. |
| pytm itself | `metadata.tools.components[0]` (`application`, `pytm`, version) | Version is empty when run from a source tree (not installed). |
| `TM.name`, `TM.description` | `metadata.component` (`type: application`, `name`, `description`) and `blueprints[0].name/description` | The modelled system is declared as an *application* component. This is a guess: pytm does not know whether the system is an application, service, platform, etc. |
| `TM` | `blueprints[0]` with `modelTypes: ["data-flow"]` | One blueprint per run. |

## 2. Elements

| pytm element | TM-BOM target | Attributes translated | Notes / caveats |
|--------------|---------------|-----------------------|-----------------|
| `Boundary` | `blueprints[].zones[]` (`type: trust`) | `name`→`name`; `description`→`description`; `inBoundary`→`parent` (zone ref); `inScope`→`pytm:inScope` | pytm boundaries are *regions* (zones). The TM-BOM `boundaries[]` entry is the *line between two zones* (see next row), so the concept is split in two. |
| (derived from `Dataflow`) | `blueprints[].boundaries[]` (`type: trust`, `zones: [a, b]`) | One per unordered pair of zones that at least one flow crosses; `name` = `"A <-> B"` | pytm has no such object. Only crossings made by flows are recorded; two adjacent zones with no flow between them get no boundary. Schema requires ≥2 zones, so a boundary is never emitted for a flow inside one zone. |
| (derived) | implicit zone `zone-unbounded` / "Unbounded" | Added only when at least one boundary exists *and* some element has `inBoundary = None` | Lets flows from unplaced elements still cross a boundary. If the model has no boundaries at all, no zones/boundaries are emitted. |
| `Actor` | `blueprints[].assets[]` (`type: actor`), or `actors[]` when `kind` is set | `name`, `description`, `inBoundary`→`zone`, `maxClassification`→`classification.classification`, `inScope`, `protocol`, `port`, `isAdmin` (only when true), enabled `controls` → `pytm:*` | `actors[]` requires a `party` (organization / person / system / persona). pytm used to not know which, so actors stayed assets; setting the new `Actor.kind` now emits a real `actors[]` entry instead (see the new-attributes table). Actors with `kind` unset still come out as assets, so tools looking for `actors[]` won't find those. |
| `Server` | `assets[]` (`type: service`) | as `Actor` (plus `OS`) | Server-specific flags (`usesSessionTokens`, `usesCache`, `usesXMLParser`, ...) are **not** translated (see §4). |
| `Process` | `assets[]` (`type: process`) | as above | |
| `Lambda` | `assets[]` (`type: function`) | as above | |
| `ExternalEntity` | `assets[]` (`type: system`) | as above | "system" is the closest predefined type; a custom type could carry the original name. |
| `Agent` | `assets[]` (`type: agent`) | as above | AI-specific flags not translated. |
| `LLM` | `assets[]` (`type: model`) | as above | AI-specific flags not translated. |
| other `Asset` subclasses | `assets[]` (`type: component`) | as above | Fallback. |
| `Datastore` | `blueprints[].dataStores[]` | `name`, `description`, `inBoundary`→`zone`, `type`, `dataSets`, `isSQL`, `isShared`, `onRDS`, plus the asset properties above | `DatastoreType` mapping: `SQL`→`relational`, `FILE_SYSTEM`→`file`, `LDAP`→`hierarchical`, `AWS_S3`→`object`, `UNKNOWN`→custom `{name: "unknown"}` (type is mandatory). `isSQL` defaults to true in pytm, so it is always emitted even for non-SQL types and may contradict `type`. `dataSets` is *inferred*: the `Data` carried by flows whose sink is this store; pytm's own `Data.processedBy` is not used. |
| `Data` | `blueprints[].dataSets[]` | `name`, `description` (falls back to `name`, schema requires non-empty), `classification`, `format`, `isPII`, `isCredentials`, `credentialsLife`, `isStored` → `pytm:*`; at-rest encryption → `placements` | The data-set schema has no classification field, so classification is a property here (and a real field on assets). Booleans are emitted only when true. |
| `Dataflow` | `blueprints[].flows[]` (`type: data`) | `name`; `description`; `source`/`sink`→`source`/`destination`; `protocol`→`protocols[0]`; `tlsVersion`≠NONE→`encrypted: true`; `order`→`sequence`; `isEncrypted`→`encrypted`; `usesSessionTokens`→`authentication`; `response`→`synchronous`; `data`→`dataObjects[]` (`name`, `description`); `note`, `srcPort`, `dstPort`, `tlsVersion` (name), `usesVPN`, `isResponse`, `responseTo` (flow ref), `inScope`, enabled controls → `pytm:*` | `encrypted` comes from `Dataflow.isEncrypted` when set; otherwise it is `true` when a TLS version is set and omitted else, because "no TLS" ≠ "known unencrypted" (a non-TLS protocol such as SSH would be mis-labelled). Responses are ordinary flows; the link is only `pytm:responseTo`. `dataObjects` are inline copies linked to data sets by *name only*, not by ref. |
| `Assumption` (`TM.assumptions`, `Element.assumptions`) | `blueprints[].assumptions[]` | `name` + `description`→`description` (`"name: description"` when both); `exclude`→`impact` (`"Excludes threats: A, B"`); owning element→`relatedAssets` | The schema has no structure for "excludes threat X", so it is free text in `impact`. Element-level assumptions reference their element; global ones have none. Assumptions attached to flows are included; those attached to boundaries are not. An assumption with neither name nor description is dropped. |
| `Classification` | `assets[].classification.classification` (from `maxClassification`) | `PUBLIC`→`public`, `RESTRICTED`→`restricted`, `SENSITIVE`→`confidential`, `SECRET`/`TOP_SECRET`→`classified`, `UNKNOWN`→omitted | `SECRET` and `TOP_SECRET` collapse into one value (lossy). |
| `Controls` (`Element.controls`) | `pytm:controls.<name>` properties | Every control that is true / non-empty (e.g. `isEncrypted`, `authenticationScheme`) | Only *enabled* controls appear. They are not translated into TM-BOM `controls`, see §5. |

## 3. Findings

| pytm | TM-BOM | Attributes | Notes / caveats |
|------|--------|-----------|-----------------|
| Findings + excluded findings, grouped by threat SID | `threats.threats[]` (`bom-ref: threat-<sid>`) | `description`→`name`; `details`→`description`; `source: "pytm"`; `stride`→`categories`; `cwe`→`weaknesses`; `capec`→`attackPatterns`; controls with matching `mitigates`→`mitigations`; affected elements (any element kind, deduplicated)→`affectedAssets`; http(s) links in `references`→`externalReferences` (`type: other`); `threat_id`, `severity`, `likelihood`, `condition`, `mitigations`, `example`, `references` → `pytm:*` | One TM-BOM threat per SID, shared by all elements it hit, whereas pytm has one finding per element × threat. Taken from the first finding of the group. `categories` is omitted when `stride` is empty (custom threat files). The library's free-text `mitigations` stays in `pytm:mitigations`; the TM-BOM `mitigations` field holds references to declared `Control`s. CVE ids and non-CAPEC/CWE references are only kept inside `pytm:references`. A threat appears here even if all its findings were excluded. |
| `Finding` | `risks.risks[]` (`bom-ref: risk-<id>`) | `description` + `target`→`name`; `details`→`statement`; element→`affects`; SID→`relatedThreats`; `severity`→`inherentRisk.score.level`; `likelihood`→`inherentRisk.likelihood.level`; `impact`→`inherentRisk.impact.level`; linked controls→`responses[0].controls`; `response`→`responses[0].strategy` and `status`; `mitigations`→`responses[0].description`; `cvss`, `id` → `pytm:*`; `domains: [security]` | Severity: `Very High`/`Critical`→`critical`, `High`→`high`, `Medium`→`medium`, `Low`→`low`, `Very Low`→`info`. Likelihood: lower-cased and hyphenated, empty → omitted. Response: `mitigated`→`reduce`/`mitigated`, `transferred`→`transfer`/`transferred`, `accepted`→`accept`/`accepted`, `avoided`→`avoid`/`retired`; no response → status `identified`, no response entry. `impact` is only present when set (see above): pytm severity blends likelihood and impact and cannot be split. `retired` for "avoided" is a judgement call. |
| Excluded `Finding` (suppressed by an assumption) | `risks.risks[]` (`bom-ref: risk-excluded-<id>`) | as above, `description`: `"Excluded by assumption: <name>"` | Forced to status `accepted` with an `accept` response. Without this the excluded threats would silently vanish from the BOM. |

## 4. pytm attributes not translated

Dropped without a `pytm:` property:

* Element: `levels`, `sourceFiles`, `overrides`, `severity` (the 0–5 element
  rollup), `minTLSVersion`, `uuid` (random, not stable).
* Asset: `onAWS`, `handlesResources`, `usesEnvironmentVariables`, `inputs`,
  `outputs`, `data` (default incoming data).
* Server / Process / Lambda / Agent / LLM / Datastore specific booleans other
  than `isSQL`, `isShared`, `onRDS`.
* Data: `carriedBy`, `processedBy`.
* Dataflow: `implementsCommunicationProtocol`.
* TM: `isOrdered`, `mergeResponses`, `ignoreUnused`, `onDuplicates`,
  `threatsFile`, `colormap`.
* Finding: `condition` appears only on the threat, not the risk.

Not emitted at all (sections of the TM-BOM with no pytm counterpart or no
reliable data): `components`, `services`, `dependencies`,
`visualizations`, `useCases`, `requirements`, `scope`,
`attackTrees`/`attackPaths`, `threats.methodologies`,
`threatProfiles`.

## 5. Trade-offs

1. **Pinned to an unpublished draft.** Output is validated against a specific
   2.0 draft commit. Field names and enums may move before release; each bump
   needs `COMMIT` in `tests/fetch_cyclonedx_schema.sh` (and `SCHEMA_COMMIT` in
   `pytm/tmbom.py`) updated and the mapping rechecked. The schema is not
   committed; the validation tests skip when it has not been fetched. Consumers built for a later draft may reject the file.
2. **Fidelity vs. validity.** Everything with no schema field goes into
   `pytm:` string properties (booleans become `"true"`). This keeps the BOM
   valid and lossless-ish, but tools will ignore them, and values are untyped.
3. **No invented data, but it is now the modeller's job.** Actor party, impact,
   control status and explicit encryption are only exported when set; the
   defaults stay "unknown" and are omitted. STRIDE is `unassigned` (and omitted)
   for every bundled threat.
4. **Threat deduplication.** One threat per SID with a list of affected assets
   matches the TM-BOM model but loses per-element detail from the threat
   (that detail survives in the per-finding risks). Threat text comes from the
   first finding in the group.
5. **Findings as risks.** Every finding becomes a risk, so a model with many
   findings yields a large `risks` section (139 for the sample). It is
   complete but noisy; there is no aggregation or prioritisation.
6. **Two notions of control.** The library's `mitigations` are still advice
   text, and the `Controls` boolean flags still drive threat conditions and are
   exported as properties. Only the new `Control` objects become TM-BOM
   `controls`, and declaring one does not suppress findings or change
   `resolve()`; linking is export-only. `Control` vs `Controls` is an easy
   name clash.
7. **Inferred structure.** Boundaries are derived from flows, the unbounded
   zone is synthesised, and data-store `dataSets` come from flow sinks. These
   are reasonable but not facts in the pytm model.
8. **Name-based identity.** Refs derive from names (pytm has no stable ids), so
   renaming an element changes its `bom-ref`; same-named elements get numeric
   suffixes whose order depends on creation order.
9. **Non-reproducible by default.** `serialNumber` and `timestamp` change each
   run. Tests inject fixed values via `build_tmbom(...)`; the CLI does not
   offer a flag to do so.
10. **Output to stdout only**, like `--report`, rather than a file like
    `--json`; use shell redirection. Resolution (`TM.resolve()`) is run
    implicitly, so `--exclude` applies.
11. **No import path.** `--tmbom` is export only; `pytm.load` still reads only
    pytm's own `--json` format.
